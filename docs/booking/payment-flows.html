Como fluye el pago de una reserva

Todo pago pasa por el mismo esqueleto — el cliente solicita, el propietario aprueba, el cliente paga, el propietario confirma — pero tres cosas cambian segun la configuracion de cada local: si hace falta que el propietario apruebe cada solicitud a mano, cuantos pagos hacen falta y de que tamano, y si el local tiene un precio publicado o pide cotizacion. Hoy nada de esto es configurable: todo local pide aprobacion manual, pide el mismo 30% de anticipo fijo, y necesita un precio publicado. Los diagramas 2 a 5 muestran las opciones que se estan planificando para que cada propietario elija las suyas.

● Vigente hoy en produccion ● Planeado — docs/booking/pricing-and-payments.md
Uno

El flujo de hoy — anticipo fijo del 30%

El unico flujo que existe en produccion ahora mismo. No hay forma de que un propietario pida pago completo por adelantado, ni de ajustar el porcentaje del anticipo — y una vez pagado el anticipo, no hay ninguna pantalla para pagar el saldo restante. La aprobacion manual del propietario tampoco se puede saltar hoy: existe una casilla “Reserva inmediata” en el formulario del local, pero no esta conectada a nada todavia (ver diagrama 4).

Tres

Cuatro

Reserva inmediata — saltar la aprobacion manual

Idea nueva para la Fase 1: algunos propietarios manejan su calendario 100% desde la app y no quieren revisar cada solicitud a mano — si las fechas estan libres, quieren que la reserva quede confirmada al toque. La base ya existe (Venue.instantBooking, incluida la casilla en el formulario del propietario) pero hoy no hace nada — falta conectarla en BookingService.requestBooking(). La validacion de disponibilidad y el calculo de precio no cambian; lo unico que se salta es el paso de aprobar/rechazar.

Cinco

Modo “Cotizar” — locales sin precio fijo

Idea nueva para una Fase futura (5): locales que cobran “segun el evento” y no pueden publicar un precio fijo real. En vez de precio + reservar, el detalle del local muestra “Consultar precio” y un boton “Cotizar” que abre el contacto con el propietario. Recien cuando el propietario le pone un precio a esa solicitud puntual se convierte en una reserva de verdad y entra al mismo flujo de siempre.

Cuando el flujo no llega a completarse

De paso, algo que encontramos revisando el codigo: el cliente solo puede cancelar mientras la reserva esta PENDING o APPROVED. El propietario, hoy, solo puede rechazar mientras esta PENDING (o marcarla NO_SHOW desde APPROVED) — una vez que el anticipo esta pagado, no hay ningun boton para que el propietario cancele. Existe un metodo canBeCancelledByOwner() en el codigo que ya contempla DEPOSIT_PAID, pero no esta conectado a ningun endpoint todavia.
